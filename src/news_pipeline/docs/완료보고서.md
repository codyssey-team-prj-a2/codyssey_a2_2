작성일: 2026-08-06

## 1. 개요

뉴스를 자동 수집(RSS/API/크롤링) → 정제 → AI 요약 → AI 인사이트 분석 → 시각화 → 리포트 → 내보내기까지 처리하는 CLI 기반 Python 애플리케이션을 `docs/../실행지시서`(대화 중 전달된 지시서) 기준으로 구현했습니다. 필수 기능과 보너스 기능(조회 CLI, 감성 분석, 스케줄링 문서화)을 모두 포함했습니다.

- 저장소: 로컬 git 저장소(`git init`), Phase 단위로 총 **14개 커밋**, 전부 한글 메시지
- GitHub 원격 저장소에는 아직 푸시하지 않음(요청대로 로컬 이력만 보존)

## 4. 실행 검증 근거 (최종 통합 테스트 기준)

```
fetch --source all --limit 6   → rss 6건 / api 6건 / crawl 6건 = 총 18건 (raw)
clean                          → raw 18건 중 신규 17건 저장, 중복 1건 스킵
summarize --unsummarized       → 누적 8건 요약 성공
sentiment --unanalyzed         → 누적 6건 감성 분류 성공
analyze --category IT          → 실제 Gemini 응답으로 트렌드/키워드/시사점 산출 및 저장
report --format md             → 정제율 94.4%, 요약완료율 47.1%, TOP5 카테고리, 차트 3종 포함 리포트 생성
export --format csv/excel      → csv 17건, excel(--status summarized) 8건 파일 생성
```

에러 케이스도 별도로 검증:
- 존재하지 않는 도메인으로 fetch → 3가지 수집 방식 모두 예외 없이 빈 리스트 반환 + 로그 기록
- `GEMINI_API_KEY` 미설정 상태로 summarize 호출 → 명확한 안내 메시지 후 종료(크래시 없음)

## 5. 알려진 제한사항

- **Gemini 무료 티어 쿼터**: 모델/계정에 따라 하루 요청 수가 제한됨(`docs/이슈노트.md` 5번 참고). 대량으로 `summarize`/`analyze`/`sentiment`를 돌리면 실패가 늘어날 수 있음 — `--limit`을 작게 잡고 나눠서 실행 권장.
- **위키백과 크롤링 소스**: "포털:최근 사건" 페이지는 하루 갱신량이 적어(테스트 시점 7건) 대량 수집에는 부적합. 학습/테스트 목적의 예시 소스로 등록한 것이며, 실제 서비스 시엔 `config add-source`로 다른 크롤링 대상을 추가하는 것을 권장.
- **published_at 정확도**: 위키백과 크롤링은 "N월 N일"처럼 연도가 없는 날짜 표기를 현재 연도로 보정해서 저장함 — 연말/연초 경계에서는 오차가 생길 수 있음.
- **날짜 필터(list/analyze 등)**: `published_at`의 앞 10자(YYYY-MM-DD)로 문자열 비교하므로, 매우 드물게 타임존 경계값에서 하루 오차가 있을 수 있음.

## 7. 갱신 이력 — 2026-08-09: 팀 Notion 스펙 문서("개발로직") 정렬

팀 저장소의 Notion 스펙 문서를 확인해 기존 구현과 대조한 결과, config/env 구조·품질지표 2종·CLI 옵션 일부가 스펙과 달랐던 부분을 전부 반영했습니다. 총 9개 커밋으로 나눠 진행했습니다.

| 항목 | 이전 | 이후 |
|---|---|---|
| `config.json` 구조 | `sources`/`duplicate_policy`/`request_delay_sec` 평면 구조 | 스펙대로 `news_sources`/`storage`/`fetch`/`ai`/`report`/`logging` 섹션화 |
| `.env` | `GEMINI_API_KEY` (Gemini 전용) | `LLM_PROVIDER`/`LLM_MODEL`/`LLM_API_KEY` (범용) |
| AI 프로바이더 | Google Gemini만 지원 | OpenAI(GPT)/Anthropic(Claude)/Google(Gemini) 중 선택(`src/ai_client.py`) |
| DB/로그 저장 경로 | `db.py`/`logger.py`에 하드코딩 | `config set-db-path`/`config set-log`로 설정 가능(`data/news_pipeline.db`로 파일명도 스펙 예시에 맞춤) |
| HTTP 타임아웃 | `collector.py`에 상수 하드코딩(10) | `config.json`의 `fetch.timeout_sec`로 설정 가능 |
| 리포트 품질지표 | 정제율, 요약 완료율 2종 | **중복 수집 방지율** 추가(스펙의 3종 지표 모두 구현) |
| 리포트 TOP N | 카테고리 TOP5만 | 카테고리 **TOP3** + **핵심 키워드 TOP5**(`collections.Counter` 집계, 스펙 값 그대로) |
| `analyze` 기간 미지정 시 | 전체 DB 조회 | 최근 7일 기본 적용(스펙의 "메모리 보호" 리뷰 포인트 반영) |
| `export` 옵션 | `--format`/`--status`만 | `--date-from`/`--date-to` 추가 |
| 리포트/차트/내보내기 저장 위치 | 각 모듈에 경로 하드코딩 | `config.json`의 `report.output_dir` 기준으로 통일 |

세부 설계 결정(특히 import-linter 레이어 규칙 때문에 `configure()` 주입 패턴을 쓴 이유, 멀티 프로바이더 재시도 로직을 하나로 유지한 방법)은 `docs/이슈노트.md` 7·8번에, 관련 설계 패턴 설명은 `docs/학습가이드.md`의 "목표 6"에 정리했습니다.

**검증 방법**: 실제 Gemini API 1회 호출로 멀티 프로바이더 회귀를 확인했고, `fetch`/`clean`/`report`/`export`/`list`/`show`/`config set-db-path` 등은 실제 명령 실행으로 확인했습니다. `analyze`/`summarize`/`sentiment`의 대량 호출은 무료 API 쿼터 보호를 위해 `unittest.mock`으로 AI 응답만 모킹해 로직(예: 최근 7일 기본값 계산)을 검증했습니다. `ruff check .`와 `lint-imports` 모두 통과.

## 8. 갱신 이력 — 2026-08-09(계속): 감성 분포 파이 차트 + 목록 정렬 수정

사용자 피드백으로 2가지를 추가 수정했습니다.

| 항목 | 이전 | 이후 |
|---|---|---|
| 감성 분포 차트 | 막대그래프 | 파이 차트(비율 % 라벨 포함) — `visualizer.chart_sentiment_distribution()` |
| `list`/`browse`/`pick_id` 기본 정렬 | `collected_at`(수집 시각) 기준 | `published_at`(발행일) 기준 — 화면에 보여주는 컬럼과 정렬 기준을 일치시킴 |
| 정렬 동점 처리 | 없음(2차 기준 없음) | 모든 정렬 기준에 `id DESC`를 2차 기준으로 추가 |

**발견 경위**: 사용자가 "목록 정렬이 뒤죽박죽"이라고 지적. 확인해보니 화면엔 발행일을 보여주면서 정렬은 수집 시각 기준이라 생긴 불일치였음(1차 수정). 이후 "날짜순은 맞는데 ID가 종종 뒤죽박죽"이라는 재지적을 받고 DB를 조사한 결과, `published_at`이 초 단위까지 완전히 같은 기사가 실제로 존재해서(같은 배치로 수집된 기사 등) 1차 정렬 기준만으로는 동점 안에서 SQLite가 순서를 보장하지 않는다는 걸 확인함(2차 수정). 자세한 원인 분석은 `docs/이슈노트.md` 9번 참고.

**검증 방법**: `db.query_news()`를 반복 호출해 동점 그룹의 순서가 매번 동일하게 나오는지 확인. `report` 명령으로 실제 파이 차트 PNG를 생성해 한글 라벨이 정상 출력되는지 육안 확인.
