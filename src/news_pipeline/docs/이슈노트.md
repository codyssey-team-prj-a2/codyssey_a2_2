## 1. Windows 콘솔에서 한글이 깨져 보임

**증상**: `rich`로 한글을 출력했는데 콘솔에 `�Ϸ� ui ��� ���� ����` 같은 글자가 찍힘.

**원인**: Windows 콘솔의 기본 코드페이지(cp949)와 Python의 stdout 인코딩이 맞지 않음. 코드 자체는 정상이었고(`PYTHONIOENCODING=utf-8`을 주면 바로 정상 출력됨), 순수히 터미널 인코딩 문제였음.

**해결**: `main.py` 최상단에서 `sys.stdout.reconfigure(encoding="utf-8")` / `sys.stderr.reconfigure(encoding="utf-8")`를 호출해, 사용자가 어떤 콘솔 설정으로 실행하든 항상 UTF-8로 출력되게 고정함.

## 2. `google-generativeai`가 아니라 `google-genai`를 써야 함

**증상**: 계획 단계에서는 `anthropic` SDK를 상정했으나, 사용자가 Google AI Studio 무료 키로 방향을 바꾸면서 Gemini SDK를 조사함.

**확인한 사실**: 레거시 패키지 `google-generativeai`는 2025-11-30부로 지원 종료(deprecated)되었고, 현재는 `google-genai` 패키지(`from google import genai`)가 표준. 설치된 패키지의 실제 시그니처를 `inspect`로 직접 확인해서 문서에 의존하지 않고 검증함.

```python
client = genai.Client(api_key=API_KEY)
client.models.generate_content(model="...", contents="...", config=types.GenerateContentConfig(...))
```

**참고**: `GenerateContentConfig`에 `system_instruction`, `response_mime_type="application/json"` 필드가 있어서 JSON 강제 출력이 가능함(analyzer/sentiment에서 활용).

## 3. `GOOGLE_API_KEY`와 `GEMINI_API_KEY`가 동시에 있으면 경고가 뜸

**증상**: `.env`에 `GEMINI_API_KEY`를 등록했는데도 실행 시 `Both GOOGLE_API_KEY and GEMINI_API_KEY are set. Using GOOGLE_API_KEY.` 경고가 콘솔에 직접 찍힘.

**원인**: 이 PC의 다른 환경(예: anaconda)에 이미 `GOOGLE_API_KEY`가 전역 환경변수로 설정돼 있었음. `google-genai`는 `Client(api_key=...)`처럼 **명시적으로 키를 넘기면 그 값이 우선**한다(SDK 공식 테스트 코드 `test_mldev_explicit_arg_precedence`로 직접 확인). 다만 내부 로거가 "둘 다 있다"는 경고를 무조건 찍기 때문에, 실제로는 우리가 지정한 키가 쓰이는데도 마치 문제가 있는 것처럼 보임.
또한 이 경고가 우리 앱의 로깅 규칙(화면=rich, 파일=logging 분리)을 깨고 SDK 내부 로거가 화면에 직접 출력하는 문제도 있었음.

**해결**: `ai_client.py`에서 `logging.getLogger("google_genai._api_client").setLevel(logging.ERROR)`로 해당 경고를 억제. 우리 코드는 항상 `.env`의 `GEMINI_API_KEY`를 명시적으로 넘기므로 동작에는 문제 없음.

## 4. Google 뉴스 RSS의 요약 필드에 HTML 태그가 섞여 나옴

**증상**: RSS로 수집한 기사의 `content`(summary)에 `<a href="...">제목</a>` 같은 HTML 원문이 그대로 들어있었음.

**원인**: Google News RSS는 `description` 필드에 순수 텍스트가 아니라 HTML 마크업을 그대로 내려줌(공식 사양이 아니라 실제 응답을 보고 확인).

**해결**: 애초에 지시서의 "정제(clean) 단계 = 텍스트 정규화" 요구사항이 이걸 위한 것이었음. `cleaner.py`의 `_normalize_text()`에서 `BeautifulSoup(text, "html.parser").get_text()`로 태그를 제거하고 공백을 정리함. raw 데이터는 원본 그대로 보존(가공하지 않음)하고, clean DB에만 정규화된 텍스트가 들어감 — raw/clean을 분리해서 저장하는 설계가 실제로 이런 상황에서 빛을 봄(정제 로직에 버그가 있어도 raw를 다시 정제하면 복구 가능).

## 5. Gemini 무료 티어의 실제 한도를 에러 메시지로 발견

**증상**: 통합 테스트 중 `summarize`/`sentiment`를 연달아 돌렸더니 절반 이상이 실패함.

**원인 조사**: 처음엔 503(`UNAVAILABLE`, "서버가 일시적으로 붐빔") 에러였다가, 이어서 429(`RESOURCE_EXHAUSTED`) 에러의 상세 메시지에서 다음 정보를 확인함.

```
Quota exceeded for metric: generativelanguage.googleapis.com/generate_content_free_tier_requests
quotaId: GenerateRequestsPerDayPerProjectPerModel-FreeTier
quotaValue: 20   (model: gemini-2.5-flash)
```

즉 이 계정에서 `gemini-2.5-flash`는 **모델당 하루 20회**로 제한되어 있었고, 테스트하면서 이미 그 한도를 다 써버린 것. (참고: 무료 티어 한도는 계정/시점마다 달라질 수 있어 공식 문서에 고정 수치로 나오지 않음 — [Google AI Studio rate-limit 페이지](https://aistudio.google.com/rate-limit)에서 실시간 확인 필요.)

**추가로 확인한 것**: 대체 모델로 `gemini-2.5-flash-lite`를 시도했더니 `404 NOT_FOUND: This model ... is no longer available to new users.`— 이미 신규 사용자에게는 제공되지 않는 모델이었음. 대신 `gemini-3.5-flash-lite`는 별도 쿼터로 정상 동작함을 확인.

**해결**:
1. `config.json`의 기본 모델을 `gemini-3.5-flash-lite`로 변경(모델별로 쿼터가 분리되어 있어 우회 가능했음).
2. `ai_client.py`의 재시도 로직을 429뿐 아니라 5xx(500/502/503/504)까지 지수 백오프 대상에 포함하도록 수정 — 원래는 429만 백오프하고 503은 짧게 고정 지연 후 바로 포기해서 재시도가 무의미했음.
3. API 호출 전에 `ai_client.has_api_key()`로 키 존재를 먼저 확인해서, 키가 없을 때 "N건 실패"로만 나오던 것을 명확한 안내 메시지로 조기 종료하도록 개선.

## 6. 크롤링 대상은 "실제로 확인 가능한 곳"으로 골라야 함

지시서에는 크롤링 대상이 `example-news-site.com` 같은 예시로만 적혀 있어서, 실제 사이트를 정해야 했음. 후보를 고를 때 다음을 미리 확인함.

- `robots.txt`가 일반 크롤러를 막지 않는지 (`ko.wikipedia.org/robots.txt` 확인)
- 실제 응답이 200인지, HTML 구조가 예측 가능하고 안정적인지(`div.mw-parser-output` 안의 `<li>` 목록)

최종적으로 위키백과 "포털:최근 사건" 페이지를 선택. 다만 이 페이지는 하루 수 건 정도만 갱신되므로(테스트 시점엔 7건), 대량 수집용으로는 적합하지 않고 **테스트/학습용**이라는 한계가 있음(원 지시서도 "테스트용으로 쉬운 사이트 아무거나"를 요구했으므로 이 목적에는 부합).

## 7. (2026-08-09) import-linter 레이어 규칙 때문에 "설정 주입" 패턴이 필요했음

**배경**: 팀 Notion 스펙 문서("개발로직")에 맞춰 `config.json`을 재구성하면서, DB 경로(`storage.db_path`)와 로그 경로/수준(`logging.*`)도 하드코딩 대신 설정 파일로 옮기려 했음.

**증상**: `db.py`나 `logger.py`에서 그냥 `from src import config_loader`를 추가하고 값을 읽으면 될 줄 알았는데, `lint-imports`가 계약 위반으로 막음.

**원인**: `pyproject.toml`의 import-linter 레이어 설정을 보면 `db | raw_store | config_loader | logger | ui`가 같은 최하위 계층에 **나란히(`|`)** 묶여 있음. 이건 "이 모듈들끼리는 서로 몰라야 한다"는 의도적 설계(순환 참조/숨은 결합 방지)라서, `db.py`가 `config_loader.py`를 직접 import하면 "같은 계층끼리 import"로 계약 위반이 남.

**해결**: 각 모듈에 `configure(...)` 함수를 추가해 "설정값을 스스로 읽어오지 않고, 밖에서 주입받는" 방식으로 바꿈. 실제로 config를 읽어서 주입해주는 역할은 `src` 패키지 바깥에 있는 `main.py`가 맡음(`main.py`는 import-linter의 `root_package = "src"` 범위 밖이라 뭐든 import해도 계약 위반이 아님).

```python
# main.py — cli/menu를 import하기 "전에" 먼저 설정을 주입해야 한다
config_loader.load_env()
_config = config_loader.load_config()
logger_mod.configure(_config.get("logging", {}))   # 반드시 가장 먼저
db.configure(_config.get("storage", {}).get("db_path"))
raw_store.configure(_config.get("storage", {}).get("raw_dir"))

from src import cli, menu  # 이 시점부터 import되는 모듈들이 새 설정을 보게 됨
```

**함정**: `logger.configure()`는 특히 순서가 중요했음. `menu.py`를 import하면 그 안에서 연쇄적으로 십여 개 모듈이 import되고, 각 모듈 최상단의 `log = get_logger(__name__)` 호출이 `setup_logging()`을 그 즉시 실행시켜버림(`_configured` 플래그로 한 번만 실행). 즉 `cli, menu`를 먼저 import하고 나중에 `logger.configure()`를 부르면 이미 늦음 — 파일 핸들러가 옛 경로로 고정된 뒤이기 때문. 그래서 `configure()` 호출들을 `from src import cli, menu`보다 앞에 두는 순서가 필수였음.

**교훈**: 계층형 아키텍처(레이어드 아키텍처) 규칙은 "모듈 A가 모듈 B를 알아야 하는가?"를 도구로 강제하는 것인데, 값 하나를 전달하기 위해 규칙을 어기기보다는 "밖에서 주입"하는 게 더 건강한 설계라는 걸 실제로 겪어봄. 반대로 URL 정규화 로직처럼 `cleaner.py`와 `reporter.py`(같은 계층, 서로 sibling)가 공유해야 하는 순수 함수는, 아예 더 아래 계층에 새 모듈(`src/normalize.py`)을 만들어 옮기는 방식으로 해결함.

## 8. (2026-08-09) 멀티 프로바이더(OpenAI/Anthropic/Google) 지원 시 재시도 로직을 어떻게 하나로 유지했는가

**배경**: 처음엔 Gemini(`google-genai`) 전용으로 짰던 `ai_client.py`를, 팀 스펙 문서의 초기 설정 마법사(GPT/Gemini/Claude 중 선택)에 맞춰 3개 프로바이더를 다 지원하도록 바꿔야 했음.

**문제**: 세 SDK(`openai`, `anthropic`, `google-genai`)는 클라이언트 생성 방식, 메시지 포맷(`system` 파라미터 위치, `max_tokens` 필수 여부), JSON 강제 출력 방식이 전부 다름. 기존처럼 `generate()` 함수 하나에 if/elif로 다 욱여넣으면 함수가 급격히 커지고 인자도 6개를 넘어감(`ruff`의 `max-args=5` 가드에도 걸림).

**해결**:
1. 프로바이더별 호출부를 `_call_openai()`/`_call_anthropic()`/`_call_google()` 세 개의 작은 함수로 분리하고, `PROVIDER_HANDLERS` 딕셔너리로 디스패치(if/elif 체인 대신 함수를 값으로 갖는 매핑 사용).
2. 세 함수가 받는 인자(model/system_prompt/user_prompt/api_key/json_output/max_tokens)를 `Request`라는 `NamedTuple` 하나로 묶어서, 함수 시그니처는 전부 `(req: Request) -> str`로 통일. 인자 개수 가드도 자연히 통과.
3. 재시도/백오프 로직(`generate()`)은 프로바이더를 몰라도 되게, 각 SDK 예외 객체에서 `status_code` 또는 `code` 속성을 range-agnostic하게 뽑아내는 `_status_code()` 헬퍼 하나로 429/5xx 여부만 판단하도록 통일함. SDK마다 예외 클래스는 다르지만 우연히도 셋 다 `status_code`(OpenAI/Anthropic) 또는 `code`(google-genai) 속성을 갖고 있어서 이 방식이 통했음.

**검증**: 실제로 `.env`를 Gemini 키로 설정한 상태에서 `ai_client.generate()`를 한 번 직접 호출해 응답을 받는 것으로 회귀를 확인함(무료 API 쿼터를 아끼기 위해 `analyze`/`summarize` 전체를 돌리는 대신 단발 호출로 검증).

## 9. (2026-08-09) 목록 정렬이 "뒤죽박죽"으로 보인 두 가지 원인

**1차 증상**: 사용자가 "list 목록 정렬할 때 아직도 뒤죽박죽인 경우가 있다"고 지적.

**1차 원인**: `db.query_news()`의 기본 정렬이 `collected_at DESC`(수집 시각 기준)였는데, `viewer.py`의 `list`/`browse`/`pick_id` 화면은 정작 **발행일**(`published_at`) 컬럼을 보여주고 있었음. 즉 "정렬 기준"과 "화면에 보이는 기준"이 서로 다른 컬럼이라, 발행일만 보면 순서가 뒤죽박죽처럼 보일 수밖에 없었음. 코드만 봐서는 바로 안 보이고, 실제로 `list` 명령을 실행해서 나온 ID 순서(14, 15, 16, 17, 13, 12, 11, 27, 9, 8 ...)와 발행일 컬럼을 나란히 놓고 봐야 눈에 띄는 문제였음.

**1차 해결**: `query_news()`의 기본 정렬을 `published_at DESC`로 바꾸고, `pick_id()`가 따로 쓰던 `id DESC`도 제거해서 모두 같은 기준을 따르게 통일함.

**2차 증상**: 사용자가 재확인 후 "날짜순은 맞는 것 같은데 종종 id 숫자가 뒤죽박죽 되는 게 있다"고 다시 지적. 1차 수정만으로는 부족했다는 뜻.

**2차 원인 조사**: DB를 직접 조회해서 `published_at`이 완전히 같은 값을 가진 기사가 있는지 확인함.

```sql
SELECT published_at, COUNT(*) c FROM news GROUP BY published_at HAVING c > 1;
-- 2026-08-06T15:15:42.827955+00:00 | 2
-- 2026-08-08T22:00:00+00:00         | 2
```

실제로 초 단위까지 완전히 같은 `published_at`을 가진 기사 쌍이 있었음(같은 배치에서 수집된 기사 등). SQL의 `ORDER BY published_at DESC`처럼 정렬 기준이 하나뿐이면, 그 값이 동점인 행들 사이의 순서는 SQL 표준상 보장되지 않음 — SQLite가 내부적으로 아무 순서나 줄 수 있고, 실행할 때마다 달라질 수도 있음. 실제로 반복 호출해보면 동점 그룹(id 30/35, id 14/15) 안에서의 순서가 "정렬 기준으로는 설명이 안 되는" 배치로 나왔음.

**2차 해결**: 모든 정렬 기준(`published_at DESC`, `collected_at DESC`)에 **2차 정렬 기준으로 `id DESC`를 추가**해서 동점 자체를 없앰(`id`는 PK라 절대 동점이 안 남).

```python
_ORDER_BY_SQL = {
    ORDER_BY_PUBLISHED_DESC: "published_at DESC, id DESC",
    ORDER_BY_COLLECTED_DESC: "collected_at DESC, id DESC",
    ORDER_BY_ID_DESC: "id DESC",
}
```

**검증**: `db.query_news()`를 3번 반복 호출해서 동점 그룹의 id 순서가 매번 정확히 같게 나오는지 확인함(고침 전에는 원리상 매번 달라질 수 있는 상태였음).

**교훈**: `ORDER BY` 절에 정렬 기준을 하나만 쓰면 "그 기준으로 값이 같은 행들끼리는 순서가 정의되지 않는다"는 걸 놓치기 쉬움. 특히 이 프로젝트처럼 여러 소스에서 같은 배치로 수집하거나, 크롤링처럼 시간 정보가 날짜 단위로만 잡히는 소스가 섞여 있으면 동점이 실제로 자주 발생함. 정렬이 "가끔" 이상해 보인다면, 먼저 정렬 기준 컬럼에 중복값(동점)이 있는지 `GROUP BY ... HAVING COUNT(*) > 1`로 확인해보는 게 빠른 진단법이라는 걸 배움. 해결책은 언제나 "동점이 절대 안 나는 컬럼(PK 등)을 2차 기준으로 추가"하는 것.
