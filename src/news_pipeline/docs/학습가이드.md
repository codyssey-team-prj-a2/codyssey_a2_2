# 학습 가이드 — 이 프로젝트로 무엇을 배울 수 있는가

이 문서는 원래 과제의 "과제 목표"(스스로 설명할 수 있어야 하는 것) 5가지를 기준으로, 실제로 이 프로젝트에 구현된 코드를 예시로 삼아 설명합니다. 각 절은 "개념 → 이 프로젝트에서는 어디에 있나 → 핵심 코드 → 왜 이렇게 했나" 순서로 구성했습니다. 코드를 직접 열어보면서 따라가는 걸 추천합니다.

## 목표 1. API/RSS 방식과 크롤링 방식의 장단점 비교

### 개념
외부에서 뉴스 데이터를 가져오는 방법은 크게 세 가지입니다.

| 방식 | 장점 | 단점 |
|---|---|---|
| **RSS** | 구조가 표준화돼 있어 파싱이 쉬움. 사이트 구조가 바뀌어도 잘 안 깨짐 | 모든 사이트가 제공하지 않음. 필드가 제한적(본문 전체가 없을 수 있음) |
| **공개 API** | 데이터가 구조화(JSON)돼 있어 가장 안정적. 공식적으로 허용된 방법 | 키 발급이 필요할 수 있음, 사용량 제한이 있음, 응답 스펙이 API마다 다름 |
| **크롤링** | 원하는 어떤 사이트든 시도 가능(API/RSS가 없어도 됨) | 사이트 HTML 구조가 바뀌면 바로 깨짐, 사이트 정책(robots.txt) 위반 위험, 가장 불안정 |

### 이 프로젝트에서는
`src/collector.py`에 세 함수가 나란히 구현되어 있어서 직접 비교해볼 수 있습니다.

- `fetch_via_rss()` — Google 뉴스 RSS. `feedparser`로 파싱하는데, 코드가 15줄 정도로 제일 짧습니다. 다만 실제로 받아보면 `content`(summary) 필드에 HTML 태그가 섞여 나옵니다(`docs/이슈노트.md` 4번). API/RSS라고 항상 깨끗한 데이터는 아니라는 걸 보여주는 실제 사례입니다.
- `fetch_via_api()` — Hacker News 공개 API. 먼저 `topstories.json`으로 ID 목록을 받고, 각 ID마다 `item/{id}.json`을 따로 호출합니다. **목록 조회 1번 + 아이템별 조회 N번**이라는 API의 전형적인 2단계 패턴을 보여줍니다.
- `fetch_via_crawl()` — 위키백과 페이지를 BeautifulSoup으로 파싱. `div.mw-parser-output` 안의 `<li>` 태그를 찾아서, 그 안에서 다시 `<b><a>`(굵은 글씨로 된 링크)를 찾아 제목을 뽑아내는 식으로, **HTML 구조를 직접 추측해서** 데이터를 꺼냅니다. 이 사이트의 HTML이 바뀌면 이 코드는 그대로 깨집니다 — 이게 크롤링의 근본적인 단점입니다.

세 함수 모두 결과를 **동일한 딕셔너리 형태**(`title`, `content`, `url`, `category`, `published_at` 등)로 반환하도록 통일했습니다(`run_fetch()`가 방식에 상관없이 같은 방식으로 후처리할 수 있게 하기 위함). 방식은 다르지만 출력 형태를 맞추는 것 — 이것이 여러 소스를 다루는 파이프라인의 핵심 설계입니다.

## 목표 2. 외부 API 오류 처리(타임아웃, 응답 실패 등)

### 개념
네트워크 요청은 언제든 실패할 수 있습니다(사이트가 죽어있거나, 응답이 느리거나, 우리 코드가 잘못된 URL을 요청하거나). 이걸 처리하지 않으면 프로그램 전체가 멈추거나(타임아웃 없음) 예외로 죽어버립니다(에러 처리 없음).

### 이 프로젝트에서는
`src/collector.py`의 모든 요청에 두 가지가 항상 붙어 있습니다.

```python
resp = requests.get(source["url"], timeout=HTTP_TIMEOUT, headers={"User-Agent": USER_AGENT})
resp.raise_for_status()
```
- `timeout=10` — 서버가 10초 안에 응답하지 않으면 무한 대기하지 않고 강제로 실패 처리합니다.
- `resp.raise_for_status()` — HTTP 상태 코드가 4xx/5xx면 예외를 일부러 발생시켜서, 아래 `except`에서 잡히게 만듭니다.

그리고 이걸 감싸는 패턴이 일관되게 반복됩니다.

```python
try:
    resp = requests.get(...)
    resp.raise_for_status()
except requests.RequestException as e:
    log.warning(f"[rss] {source['name']} 요청 실패: {e}")
    return []
```

**핵심은 "실패해도 빈 리스트를 반환하고 계속 진행한다"는 점**입니다. 소스 3개 중 하나가 실패해도 나머지 2개는 정상 수집되도록, 한 소스의 실패가 전체를 멈추지 않게 설계했습니다. 실제로 `docs/이슈노트.md`에서 존재하지 않는 도메인으로 테스트했을 때도 예외 없이 빈 리스트만 반환하고 넘어가는 걸 확인했습니다.

AI API 호출(`src/ai_client.py`)에는 한 단계 더 나아간 처리가 있습니다. 429(요청 한도 초과)나 503(서버 과부하) 같은 "잠시 후 다시 하면 될 수도 있는" 에러는 **지수 백오프**(재시도할 때마다 기다리는 시간을 2배씩 늘림)로 최대 5번까지 재시도합니다.

```python
wait = delay * (2**attempt) if is_retryable else delay
```
왜 이렇게 할까요? 서버가 일시적으로 붐빌 때 계속 같은 간격으로 재시도하면 서버 부담을 더 줄 수 있습니다. 기다리는 시간을 점점 늘리면(1차 8초, 2차 16초, 3차 32초...) 서버가 회복할 시간을 벌어주면서도, 무한정 기다리지는 않습니다.

## 목표 3. raw/clean 데이터를 분리 저장해야 하는 이유

### 개념
수집한 데이터를 바로 정제해서 저장하면, 나중에 "정제 로직에 버그가 있었다"는 걸 발견했을 때 **원본이 없어서 다시 정제할 수 없습니다**. 그래서 원본(raw)과 가공된 결과(clean)를 분리해서, raw는 절대 건드리지 않고 clean만 다시 만들 수 있게 합니다.

### 이 프로젝트에서는

- **raw**: `src/raw_store.py` — `data/raw/{소스이름}.jsonl` 파일에 수집한 그대로 한 줄씩 추가(append)만 합니다. 절대 수정하거나 지우지 않습니다. 같은 기사를 여러 번 수집해도 중복 걸러내기 없이 전부 쌓입니다.
- **clean**: `src/cleaner.py` → `src/db.py` — raw 전체를 읽어서, 검증(필수 필드가 있는지)·정규화(HTML 태그 제거, 공백 정리)·중복 제거를 거친 뒤에만 `data/news.db`(SQLite)에 저장합니다.

실제로 이 분리 덕분에 이득을 본 사례가 있습니다(`docs/이슈노트.md` 4번). Google 뉴스 RSS의 원본에는 HTML 태그가 섞여 있었는데, 만약 raw 저장 시점에 미리 "정제"해서 저장했다면 그 정제 로직이 부족했다는 걸 나중에 발견해도 원본이 없어 다시 처리할 수 없었을 것입니다. raw는 항상 원본 그대로 있으므로, `cleaner.py`의 정규화 로직만 고치고 `clean` 명령을 다시 실행하면 됩니다(실제로 이 프로젝트에서 `clean`을 여러 번 재실행해서 확인함).

`cleaner.py`가 중복을 판단하는 기준도 눈여겨볼 만합니다.

```python
def _normalize_url(url):
    # utm_source 같은 추적 파라미터 제거, 소문자 통일 등
    ...
existing = db.get_by_url(clean_record["url"])  # DB의 url UNIQUE 제약을 이용
```
URL에 붙는 광고 추적 파라미터(`utm_source=...` 등)까지 제거한 뒤에 비교해야, 사실은 같은 기사인데 파라미터만 다른 URL을 서로 다른 기사로 착각하지 않습니다.

## 목표 4. AI API를 호출해 텍스트를 요약·분석하는 흐름

### 개념
AI API 호출은 결국 "프롬프트(지시문 + 데이터)를 보내고 텍스트 응답을 받는" requests 호출 한 번과 비슷합니다. 다만 (1) 응답 형식을 어떻게 강제할지, (2) 실패/한도 초과를 어떻게 다룰지가 실전에서 중요해집니다.

### 이 프로젝트에서는

`src/ai_client.py`의 `generate()` 함수가 모든 AI 호출의 공통 통로입니다. 요약(`summarizer.py`), 인사이트 분석(`analyzer.py`), 감성 분석(`sentiment.py`) 세 기능이 전부 이 함수 하나를 재사용합니다 — 로직을 세 번 따로 만들지 않고 한 곳에 모아둔 것입니다.

**일반 텍스트 응답 (요약)**:
```python
# src/summarizer.py
user_prompt = f"제목: {row['title']}\n본문: {row['content']}"
summary = ai_client.generate(SYSTEM_PROMPT, user_prompt)
```
system 프롬프트로 "역할"(당신은 뉴스 에디터입니다)과 "규칙"(3문장 이내, 의견 추가 금지)을 지정하고, user 프롬프트로 실제 데이터를 넣습니다. 이렇게 역할/규칙과 데이터를 분리하면, 나중에 프롬프트 규칙만 바꾸고 싶을 때 데이터 조립 코드는 그대로 둘 수 있습니다.

**JSON 강제 응답 (인사이트 분석/감성 분석)**:
```python
# src/ai_client.py
gen_config = types.GenerateContentConfig(
    response_mime_type="application/json" if json_output else None,
)
```
분석 결과처럼 "트렌드 목록, 키워드 목록, 시사점"같이 구조화된 데이터가 필요할 때는, 그냥 텍스트로 받아서 파싱하는 것보다 `response_mime_type="application/json"`으로 **모델이 JSON만 내놓도록 강제**하는 게 훨씬 안정적입니다. 그래도 100% 보장은 아니라서, `src/analyzer.py`는 `json.loads()`가 실패하면 1회 재시도하는 안전장치를 둡니다.

```python
for attempt in range(1, 3):
    try:
        raw = ai_client.generate(SYSTEM_PROMPT, user_prompt, json_output=True)
        result = json.loads(raw)
        break
    except Exception as e:
        log.warning(f"분석 응답 파싱 실패(시도 {attempt}): {e}")
```

**실패 처리**: `summarizer.py`/`sentiment.py`는 여러 건을 순회하면서 하나씩 AI를 호출하는데, 한 건이 실패해도 전체를 멈추지 않고 그 건만 "실패"로 세고 다음 건으로 넘어갑니다. 대량 처리에서는 "하나 실패했다고 전체가 멈추면 안 된다"는 원칙이 중요합니다.

```python
try:
    summary = ai_client.generate(SYSTEM_PROMPT, user_prompt)
    db.update_summary(row["id"], summary)
    success += 1
except Exception as e:
    log.error(f"요약 실패 id={row['id']}: {e}")
    failed += 1
```

## 목표 5. 데이터를 집계하고 matplotlib으로 시각화하는 과정

### 개념
DB에 쌓인 행(row) 데이터를 사람이 보기 좋은 그림으로 바꾸려면 (1) SQL로 원하는 단위로 집계하고 → (2) matplotlib에 x축/y축 값으로 넘겨서 → (3) 파일로 저장하는 3단계를 거칩니다.

### 이 프로젝트에서는

`src/visualizer.py`의 `chart_category_distribution()`을 예로 보면:

```python
rows = conn.execute(
    "SELECT category, COUNT(*) AS cnt FROM news GROUP BY category ORDER BY cnt DESC"
).fetchall()
```
**집계**는 Python으로 하나씩 세지 않고 SQL의 `GROUP BY`에 맡깁니다 — 데이터가 많아져도 이 방식이 훨씬 빠르고 코드도 짧습니다.

```python
categories = [r["category"] for r in rows]
counts = [r["cnt"] for r in rows]
ax.bar(categories, counts, color="#4C72B0")
fig.savefig(path)
```
집계 결과를 x축 리스트, y축 리스트로 각각 뽑아서 `ax.bar()`(막대), `chart_daily_trend()`에서는 `ax.plot(..., marker="o")`(선+점)에 넘깁니다. 마지막에 `fig.savefig(path)`로 PNG 파일로 저장합니다(화면에 띄우는 `plt.show()`는 CLI 환경이라 쓰지 않음 — `matplotlib.use("Agg")`로 화면 없이 파일만 그리는 백엔드를 지정했습니다).

**한글 폰트 문제**: matplotlib 기본 폰트는 한글을 지원하지 않아서 그대로 쓰면 글자가 네모(□)로 깨집니다. `_setup_korean_font()`에서 시스템에 설치된 폰트 목록을 확인해 "맑은 고딕"이나 "나눔고딕"이 있으면 그걸로 지정합니다.

```python
available = {f.name for f in font_manager.fontManager.ttflist}
for name in ["Malgun Gothic", "NanumGothic", "AppleGothic"]:
    if name in available:
        plt.rcParams["font.family"] = name
        break
```
Windows에는 보통 "맑은 고딕"이 기본 내장되어 있어서 별도 설치 없이 바로 됩니다(이 프로젝트를 실행한 PC에서도 확인함). 폰트를 하나도 못 찾으면 경고만 남기고 그냥 진행합니다(차트 자체는 만들어지되 한글만 깨질 수 있음) — 차트 생성이 아예 실패하는 것보다는 낫다고 판단한 선택입니다.

## 더 살펴보면 좋은 것 (이 프로젝트가 추가로 보여주는 것들)

- **설정과 코드의 분리**: `config.json`에 소스/AI 모델/지연시간을 두고, 코드는 그 값을 읽기만 합니다. 소스를 추가하거나 모델을 바꿀 때 코드를 고칠 필요가 없습니다(`src/setup.py`의 `add_source()` 참고).
- **화면 출력과 로그 파일의 역할 분리**: `src/ui.py`(rich, 사람이 보는 화면)와 `src/logger.py`(파일에만 남는 기록)를 분리해서, 화면은 깔끔하게 유지하면서도 문제가 생겼을 때 `logs/app.log`에서 상세 원인을 추적할 수 있게 했습니다.
- **CLI 로직 재사용**: `src/menu.py`(대화형 메뉴)는 별도 로직을 만들지 않고 `src/cli.py`의 `cmd_*` 함수를 그대로 호출합니다. 같은 기능을 두 번 구현하지 않는 것도 중요한 설계 습관입니다.

각 개념이 실제로 어떤 문제 때문에 필요했는지는 `docs/이슈노트.md`에서 더 자세히 볼 수 있습니다.
