## 1. 프로젝트 관리 방법론: 왜 애자일(Agile)인가?

짧은 기간(약 1주일) 내에 기획부터 배포까지 완료해야 하는 본 프로젝트의 특성상, 워터폴(Waterfall) 방식 대신 애자일(Agile) - 스프린트(Sprint) 기반 방법론을 채택했습니다.

- 빠른 프로토타이핑 및 피드백: 8/6~8/13이라는 매우 짧은 기간 동안, 기획이 완벽해지기를 기다리기보다 CLI 뼈대 구축 ➔ 데이터 수집 ➔ AI 연동 ➔ 시각화 순으로 빠르게 동작하는 결과물을 만들고 점진적으로 살을 붙여나가는 방식이 리스크를 최소화합니다.

- 유연한 대응력: 외부 API 장애, 웹 크롤링 차단 등 예상치 못한 병목(Blocker) 발생 시, 애자일 방식을 통해 즉각적으로 개발 방향(예: 크롤링 ➔ RSS 우선)을 선회하고 일정을 재조정할 수 있습니다.

## 2. 일정 및 태스크 관리: Kanban, Gantt, 그리고 List View

태스크의 성격과 팀원들의 직관적인 인지를 돕기 위해 세 가지 뷰(View)를 혼합하여 사용합니다.

- 칸반 보드 (Kanban): Todo ➔ In Progress ➔ Done의 상태 흐름을 시각화합니다. 현재 팀이 어떤 작업에 병목을 겪고 있는지 한눈에 파악하고, 데일리 스크럼(Daily Scrum) 진행 시 안건으로 활용하기 최적화된 뷰입니다.

- 간트 차트 (Gantt / Timeline): 1-Depth(Phase) 단위의 굵직한 일정(환경 세팅 ➔ 파이프라인 개발 ➔ QA)이 며칠간 진행되는지 시계열로 파악하여, 전체적인 프로젝트의 데드라인을 사수하는 데 사용합니다.

- 리스트 뷰 (List / Table): 단순한 이슈 나열 리스트는 전체 작업을 한눈에 볼 수 있는 가장 효율적인 화면입니다. 특정 작업의 담당자가 누구인지, 현재 진행 상황(Status)과 우선순위(Priority)는 무엇인지를 엑셀처럼 빠르게 훑고 필터링할 수 있어 실무적인 태스크 관리에 가장 많이 활용됩니다.

## 3. 단일 플랫폼 기반 협업: GitHub Projects 활용

별도의 외부 프로젝트 관리 툴(Jira, Notion, Trello 등)을 도입하지 않고, 소스 코드가 호스팅되는 GitHub 내의 'GitHub Projects'를 단일 도구(Single Source of Truth)로 사용합니다.

- 접근성 극대화: 코드를 리뷰하고 병합하는 곳과 이슈를 관리하는 곳이 동일하여, 개발자들이 도구를 전환(Context Switching)하는 피로도 없이 자연스럽게 일정 관리에 참여할 수 있습니다.

4. 품질 보증 (QA) 전략: 브랜치 환경과 연계된 테스트 데이터 파이프라인의 신뢰성을 확보하기 위해, 브랜치 환경(Staging, Main)의 목적에 맞추어 테스트 단계를 엄격히 분리하여 진행합니다.

- 단위 테스트 (Unit Test - Staging 환경): 데이터 수집(RSS 파싱), 텍스트 정제(정규식), DB Insert 등 가장 작은 기능 단위들이 개별적으로 정상 작동하는지 검증합니다. 팀원 각자가 개발한 모듈의 기초적인 결함을 스테이징 단계에서 조기에 발견하고 수정합니다.

- 통합 라이브 테스트 (Integration Test - Main 환경): 개별 모듈 검증이 끝난 후, main 브랜치에서 수집 ➔ 정제 ➔ 요약 ➔ 시각화로 이어지는 전체 데이터 파이프라인을 관통하는 통합 시나리오 테스트를 진행합니다.

5. 브랜칭 전략 및 배포 환경: Staging ➔ Main (Live) 프로젝트 기간이 매우 짧은 점을 감안하여, 복잡한 3단계(dev➔stg➔main) 구조 대신 실용적이고 빠른 2단계 브랜치(Branch) 아키텍처를 운영합니다.

- staging (개발 및 단위 테스트 환경): 팀원들이 각자의 작업을 최초로 합치고 실험하는 공간입니다. 코드가 깨질 수 있는 자유로운 구역이며, 이곳에서 기능 단위 테스트(Unit Test)를 반복하여 수행합니다.

- main (라이브/통합 테스트 및 최종 제출 환경): 스테이징 환경에서 단위 기능이 검증된 코드들이 모이는 곳입니다. 실 서비스와 동일한 조건에서 통합(Live) 테스트와 과제목표 검증 시나리오를 수행합니다.
  - 이유: main 환경에서 최종 통합 테스트를 거쳐 오류가 없음을 확인한 직후, 추가적인 브랜치 이동 없이 그 상태 그대로 과제를 제출(Deploy)하여 '테스트 환경과 제출 코드 간의 괴리'를 원천 차단하기 위함입니다.
