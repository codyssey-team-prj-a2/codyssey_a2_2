# 실행 결과 보고서

`src/main.py` 파이프라인(fetch → clean → summarize → analyze → sentiment → report → export)을
실제 외부 뉴스 데이터 + 실제 AI API로 end-to-end 실행한 로그입니다. 아래 로그는 실제 실행 결과를 그대로 옮긴 것이며
(문구를 지어내지 않음), 현재 CLI는 각 기능의 서브메뉴 안에서 명령어를 입력하는 방식이라 프롬프트는
`Codyssey/<모듈명> >` 형태입니다.

실행 환경: Windows / Python, `src/config.json`에 등록된 뉴스 소스 기준.
AI는 `news-data-pipeline/.env`에 있는 `OPENAI_API_KEY`/`OPENAI_BASE_URL`(OpenAI 호환 게이트웨이, 모델 `gpt-5.4-nano-chat`)을
그대로 사용했습니다. 이 게이트웨이는 openai SDK의 기본 헤더 지문을 WAF가 차단해서, `ai_client.py`의 OpenAI
호출부를 SDK 대신 `requests` 직접 호출 방식으로 수정해 연동했습니다(`src/lib/common/ai_client.py`).

## 2. 데이터 정제 (clean)

```
Codyssey/clean > clean --policy upsert

[ 정제 결과 (정책: upsert) ]
  - raw 전체: 49건
  - 필수 필드 누락(제외): 0건
  - 중복 스킵: 0건
  - DB 저장(신규/갱신): 49건
```

`upsert` 정책에서는 중복 URL(news_id)도 그대로 덮어써 저장하기 때문에, raw 49건이 news_id(PK) 기준으로
자동 병합되어 실제 clean_news에 저장된 고유 레코드는 **47건**입니다(위키백과 크롤링 결과 중 동일 URL 2쌍 병합).

## 결론 / 남은 작업

- fetch(RSS/크롤링) → clean → summarize → analyze → sentiment → report(품질 지표/TOP N/차트) → export
  전체 파이프라인이 실제 외부 데이터 + 실제 AI API로 정상 동작함을 확인했습니다.
- `hackernews_api` 소스는 `api` 수집 방식이 아직 구현되지 않아 건너뛰었습니다 — 구현 시 `fetch.py`의 `FETCH_HANDLERS`에 핸들러 추가가 필요합니다.
- `ai_client.py`의 OpenAI 호출을 SDK에서 `requests` 직접 호출로 변경했습니다 — 사용 중인 OpenAI 호환 게이트웨이의 WAF가
  SDK 기본 헤더를 차단하고, 모델명도 게이트웨이가 허용하는 목록(`gpt-5.4-nano-chat` 등)으로 제한하기 때문입니다.
  실제 OpenAI API(api.openai.com)를 직접 쓸 경우엔 `LLM_MODEL`을 `gpt-4o-mini` 등으로 다시 바꾸면 됩니다.
- 요약(10건)·분석(IT 1회)·감성분석(10건)은 일부만 실행한 샘플입니다. 전체 47건에 대해 재실행하면 품질 지표/TOP N이 더 유의미해집니다.
