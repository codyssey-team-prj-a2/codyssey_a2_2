# 시스템 로그 수준(Log Level) 정의 및 운용 가이드

- **문서명**: 시스템 로그 수준 정의 및 실무 운용 가이드
- **작성일**: 2026년 8월 14일
- **목적**: 안정적인 시스템 운영과 유지보수를 위한 로그 등급별 명확한 기준 확립 및 코드 작성 가이드라인 제공

---

## 1. 개요 (Overview)

로깅(Logging)은 시스템이 실행되는 동안 발생하는 흐름, 상태 변화, 오류 등의 이벤트를 기록하는 필수적인 작업입니다. 파이썬(Python) 환경에서 로그 시스템은 상황을 스스로 판단하지 않으므로, **개발자가 상황의 심각도에 맞춰 적절한 로그 수준(Level)을 명시적으로 지정하여 코드를 작성**해야 합니다.

시스템 설정(config.json)에서 특정 로그 수준을 지정하면, **해당 수준 이상의 중요도를 가진 로그만 파일에 기록(Filtering)**되어 로그 파일의 용량을 최적화하고 가독성을 높일 수 있습니다.

---

## **용량 관리 정책 (Log Rotation)**:

- 시스템 리소스 최적화 및 디스크 용량 고갈 방지를 위해 `RotatingFileHandler` 적용
- 파일 1개당 최대 용량은 `5MB`로 제한
- 오래된 로그는 최대 `3개`까지만 백업 보관 (app.log.1, app.log.2, app.log.3)
- 이 설정을 통해 시스템의 로그 파일은 아무리 오래 실행되어도 **최대 20MB (5MB \* 4개)를 절대 넘지 않도록 안전하게 통제**됨

---

> **로그 필터링 계층 구조** `DEBUG` (가장 상세함) < `INFO` (일반) < `WARNING` (경고) < `ERROR` (오류)

## 2. 로그 수준별 상세 정의 및 적용 기준

### ① DEBUG (디버그)

- **정의**: 시스템의 내부 동작 상태를 가장 상세하게 추적하기 위한 기록입니다.
- **운용 기준**: 평상시(운영 환경)에는 로그 파일에 남기지 않으며, 개발 중이거나 원인을 알 수 없는 복잡한 버그를 추적할 때만 일시적으로 로그 수준을 `DEBUG`로 낮춰서 확인합니다.
- **적용 대상**:
  - API 통신 시 주고받는 원본 JSON/XML 데이터 (Raw Data)
  - 복잡한 함수의 진입/진출 시점 및 내부 변수의 상태값
  - DB에 전달되는 최종 SQL 쿼리문
- **코드 예시**:
  ```python
  logger.debug(f"HackerNews API 원본 응답 데이터: {raw_json_data}")
  ```

### ② INFO (정보) - _운영 환경 기본값 권장_

- **정의**: 시스템이 예상대로 정상적으로 작동하고 있음을 보여주는 일반적인 실행 흐름 기록입니다.
- **운용 기준**: 운영 환경에서 시스템이 "어떤 주요 단계를 거치고 있는지" 거시적인 관점에서 모니터링하기 위해 사용합니다. 너무 자주 발생하는 반복문 내부보다는, 하나의 큰 작업 단위가 끝났을 때 기록합니다.
- **적용 대상**:
  - 프로그램(서비스)의 시작과 종료
  - 주요 파이프라인(뉴스 수집, 데이터 정제, AI 요약 등)의 실행 완료 및 결과 통계 (예: "수집 20건 완료")
  - 사용자의 중요한 설정 변경 이력
- **코드 예시**:
  ```python
  logger.info("정기 뉴스 수집 파이프라인 실행 완료 (총 20건 수집)")
  ```

### ③ WARNING (경고)

- **정의**: 시스템이 즉시 중단되거나 치명적인 오류가 발생한 것은 아니지만, 예상치 못한 문제가 발생했거나 향후 문제가 될 여지가 있는 상황입니다.
- **운용 기준**: 프로그램은 스스로 복구하거나 해당 작업을 건너뛰고 정상 동작을 계속하지만, 관리자가 나중에 인지하고 조치할 수 있도록 기록을 남깁니다.
- **적용 대상**:
  - 외부 API 서버의 응답 지연 또는 일시적인 타임아웃 (건너뛰고 다음 소스 수집)
  - 권장되지 않는 설정값 사용
  - 수집한 데이터 중 일부 필드가 누락되어 임의의 기본값으로 대체한 경우
- **코드 예시**:
  ```python
  logger.warning("Naver RSS 응답 지연으로 이번 수집을 건너뜁니다. (Timeout: 10s)")
  ```

### ④ ERROR (오류)

- **정의**: 명확한 에러가 발생하여 시스템이 특정 요청이나 작업을 완료하지 못하고 실패한 상황입니다.
- **운용 기준**: 발생 즉시 관리자가 확인하고 원인을 파악하여 조치해야 하는 심각한 문제입니다.
- **적용 대상**:
  - 데이터베이스 연결 실패 및 쿼리 실행 에러 (권한 부족, 디스크 용량 초과 등)
  - AI API Key 만료 또는 인증 실패로 인한 요약 기능 완전 마비
  - 코드 내에서 처리하지 못한 예외(Exception) 발생
- **코드 예시**:
  ```python
  logger.error(f"DB 저장 중 치명적 에러 발생: {e}")
  ```

## 3. 실무 운용 베스트 프랙티스 (Best Practices)

### 3.1 화면 출력(UI)과 시스템 로그의 분리

CLI/TUI 기반 프로그램에서는 사용자의 가독성을 위해 화면에 출력할 때 ANSI 색상 코드(예: 빨간색 텍스트)를 사용합니다. 하지만 이 색상 코드가 로그 파일에 그대로 기록되면 분석 도구에서 텍스트가 깨져 보입니다.

- **화면(Console)**: `print()` 문과 `ui.color`를 결합하여 사용자에게 직관적으로 보여줍니다.
- **파일(System Log)**: `logger`를 사용하여 색상 코드 없이 순수한 텍스트 구조로 정갈하게 기록합니다.

### 3.2 사용자 입력 실수에 대한 처리

메뉴 번호를 잘못 입력하거나(예: 1~4 중 5를 입력), 오타를 내는 등 **"사용자의 단순 입력 오류"는 로그로 남기지 않는 것을 원칙**으로 합니다.

- **이유**: 단순 오타를 모두 로그에 기록할 경우, 정작 확인해야 할 중요한 시스템 동작 기록(INFO, ERROR)이 무의미한 오타 로그에 파묻히게 됩니다 (Log Noise 발생).
- **대응 방안**: 잘못된 입력은 화면에 `print("잘못된 입력입니다.")` 형태로 즉시 피드백만 제공하고, `logger`는 호출하지 않습니다.

### 3.3 로거(Logger)의 초기화 위치

시스템 전체에서 일관된 로그 포맷(시간, 레벨, 모듈명, 메시지)을 유지하기 위해, 로거의 설정(경로 지정, 파일 생성 등)은 프로그램의 최초 진입점(`main.py` 또는 `automation.py`)에서 **단 한 번만 초기화**해야 합니다. 이후 다른 파일에서는 `logging.getLogger(__name__)`만 호출하여 사용합니다.
